# B7B 验收报告：同平台 ABI3 wheel 复用

日期：2026-10-24。对应 [分批优化计划](optimization-plan-2026-10-23.md) B7B，验证基线为 B7A 的 `1de88675`。实现提交为 `22f3cb816e45610866c6987c31fc4ba3a32ecd2f`，位于 [草稿 PR #39](https://github.com/myhloli/DocVortex/pull/39)，以 B7A 分支为基线。

> 结论：保留本批实现。冷、热两轮均 20/20 CI 通过，原有验证覆盖保留；产品构建从 14 次降为 4 次，构建安装命令合计和 runner 占用总和均下降。整体执行跨度在这两次观察中较短，但不承诺固定端到端提速比例。

## 1. 实施依据与边界

B7A 命中 Cargo 缓存后，13 个源码安装环境仍重复编译三个工作区 crate，构建安装命令成本依然明显。因此满足 B7B 的实施前提。

本批只修改四个代码文件：

- `.github/workflows/ci.yml`：Linux x64、Windows x64、macOS ARM64 各用 CPython 3.11 构建一次 wheel；13 个原有环境下载对应平台 wheel，并独立安装依赖和执行原有检查。
- `tools/ci_wheel_reuse.py`：交接清单、来源校验、独立安装及全部产品文件摘要核验。
- `tools/ci_build_metrics.py`：支持以下载 wheel 核验安装扩展，消费端计时不调用 Rust 工具链。
- `tests/test_ci_wheel_reuse.py`：23 项交接、损坏、错误来源、安装文件、依赖约束及失败路径检查。

保留原有 8 个任务定义及其 17 个展开任务，另加 3 个 wheel 生产任务，共 20 个。原来的 Python 3.11/3.14 三平台全量测试、Linux 3.12/3.13、Pydantic 下界、ONNX Runtime 下界、PDFium 固定版本、独立安装、平台产物、字体及历史几何比较、Rust 检查继续执行。Windows ARM64 保留独立构建和 Python 3.11/3.14 ABI 核验。

生产代码、Rust 算法、发布工作流、构建 profile、公开 API 和产品版本均未改变。远端验证只包含 B7A+B7B；主工作区 B0–B4、B6A、B6B 的组合验收仍属于 B8。B5 尚未实施。

## 2. ABI 与产物来源

当前配置在 `rust/docvortex-python/Cargo.toml` 使用 `pyo3` 的 `abi3-py311`，`setup.py` 同时设置 `py_limited_api=True` 和 `cp311`，项目 Python 范围为 3.11–3.14。按 [PyO3 ABI3 说明](https://pyo3.rs/v0.28.2/building-and-distribution.html)，使用最低 Python 构建后由不同 Python 独立验证；平台和架构分别隔离，不跨平台复用。

交接链路为：

1. 生产任务恢复 Cargo 依赖缓存，仍实际编译当前工作区 crate；计时日志必须包含 release 完成和 `docvortex-python` 编译事件。
2. 唯一 `cp311-abi3` wheel 中的原生扩展摘要必须匹配本次 `build/lib*` 产物，再生成清单并上传。
3. 清单记录实际检出提交、产品源码/资源摘要、workflow run ID、平台/架构、生产工具链/编译变量、缓存状态、wheel 与扩展 SHA256。
4. 消费任务只下载当前运行、当前提交、对应平台的产物。先校验清单和归档，再用明确的 wheel 路径及 `[test]` extra 安装，保留各任务原有版本约束。
5. 核对实际包及扩展位于当前独立环境、私有协议正确、扩展匹配 wheel、安装来源 URI 正确，并逐一核验全部 432 个产品文件。源码、资源或二进制变化均失败，不回退到 checkout 构建。

同一个 workflow 的失败消费任务重跑可使用前一 attempt 的同提交产物，因此身份约束包含 run ID 而不要求 attempt 相等；生产 attempt 保留在清单中。新运行和不同提交不能复用。CI wheel 不作为发布工作流的发行物来源。

本地验证发现 uv 对本地 wheel 的 `direct_url.json` 可省略 `archive_info.hashes`。初版把这个可选字段当作必需字段而失败，已按 [PyPA Direct URL 规范](https://packaging.python.org/en/latest/specifications/direct-url-data-structure/#archive-urls) 修正：校验来源 URI；存在记录摘要时必须正确；本工具始终自行核验归档及所有安装文件的 SHA256。首次失败日志保留，并加入缺省字段回归。

所有远端 artifact ZIP 已下载并核对 GitHub 提供的 SHA256。两轮各保存 30 个 artifact，其中各有 18 份任务指标；复跑前已冻结冷缓存证据。

## 4. 成本与关键路径

B7A 数据来自同一源代码的三轮成功运行，B7B 未改变产品源码和依赖解析结果。下面保留全部观察值，不挑选最快轮次：

| 观察轮次 | 产品构建/安装命令合计 | Cargo 阶段合计 | runner 占用总和 | 任务执行跨度 | 按依赖关系计算的关键路径 |
| --- | ---: | ---: | ---: | ---: | ---: |
| B7A 冷缓存 | 916.30 s | 832.88 s | 4046 s | 534 s | 513 s |
| B7A 第一次复跑 | 823.15 s | 745.19 s | 4372 s | 1095 s | 794 s |
| B7A 第二次复跑 | 937.32 s | 800.73 s | 3960 s | 691 s | 484 s |
| B7B 冷缓存 | 327.58 s | 291.01 s | 3156 s | 487 s | 483 s |
| B7B 热缓存 | 288.93 s | 244.12 s | 3400 s | 526 s | 521 s |

产品构建/安装合计包含独立 Windows ARM64 构建，不包含 clippy；这与 B7A 报告把 clippy 一并列出的约 927/827/940 秒口径不同，不能直接混比。Cargo 时间来自 Cargo 自报完成耗时，不等于独立 CPU 编译时间。

runner 占用总和是各 job 从开始至结束的秒数相加，已经包含生产任务、上传/下载、安装、测试及收尾；它既不是工作流墙钟，也不是 GitHub 计费金额。任务执行跨度是最早 job 开始到最后 job 完成，包含调度等待。关键路径按 job 实际持续时间和依赖关系求和，包含新增生产任务的屏障，排除 job 之间的排队间隙；不能将其视为另一场真实运行。

两轮构建/安装合计都比 B7A 任一轮低；runner 占用也从 3960–4372 秒下降到 3156–3400 秒。扣除已计时 pytest 命令后的 runner 占用为 B7A 的 1698–1858 秒、B7B 的 1134–1229 秒，支持收益来自重复构建及其周边工作减少，而非仅靠测试偶然变快。

Windows 全量测试波动明显：3.11 为 231.44→356.32 秒，3.14 为 259.29→354.09 秒，导致热轮次跨度从 487 增至 526 秒。B7B 热轮次的依赖路径 521 秒也高于 B7A 最快的 484 秒，因此不声称每个 job 或每一种关键路径都变快。两轮实际跨度仍低于已记录 B7A 运行；这些是 hosted runner 观察，不是同机统计基准或未来时延保证。

## 5. 保留决策与失败排查

保留方案的依据是：相同验证覆盖和安装依赖下，产品构建由 14 次降到 4 次；完整产物等价；构建安装成本和总 runner 占用在冷、热两轮均下降；新增等待已计入关键路径，实际完成跨度未观察到净退化。

为保持 CI 配置简单，13 个消费环境共同依赖三平台 wheel 生产矩阵。这意味着一个平台构建失败会阻止所有消费任务开始。生产日志、编译身份与 wheel 清单集中在三个独立任务中；安装校验失败会明确停止，测试失败仍保留对应环境日志。同运行的消费任务复跑无需重建产品 wheel。这个依赖屏障是本批明确保留的取舍，没有为了减少等待而削减验证。
